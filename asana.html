Systems Integration & Automation

Asana Workflow Automation

Building an API‑based integration to transfer project information into downstream team workflows automatically, reducing duplicate work and preserving the context employees needed to begin execution.

The workflow was already automated.

It just stopped one step too early.

A downstream ticket was created automatically, but the information needed to complete the work stayed behind. Someone still had to find the original request and manually copy everything over.

The Project

The Challenge

PPL projects could automatically create downstream tickets for teams such as Marketing, Web Operations, and Creative, but the information entered in the original PPL request did not carry into the working ticket.

02

What I Built

I built a Node.js integration using the Asana API that detected newly created downstream tickets and automatically copied the relevant project information into them.

The Existing Workflow

The system created the work, but not the handoff.

PPL projects were long‑running, cross‑functional initiatives that could remain active for six months, seven months, or sometimes close to a year.

Once a PPL was approved, the project owner created it from an existing Asana template.

Inside that template, they could select the work they needed from different departments. If the project needed an email, Web Operations support, Creative support, or another service, they could create the appropriate departmental request from inside the PPL.

That part of the process was already automated.

Creating the request inside the PPL also created a corresponding ticket in the appropriate team's queue.

But the downstream ticket was essentially blank.

The information the project owner had already entered remained in the original PPL request instead of following the work into the team's execution queue.

The Broken Handoff

  • PPL owner entered request information once
  • Asana created the downstream team ticket automatically
  • Request details did not transfer with the ticket
  • Assigned employees had to reconstruct the handoff manually
The automation already existed to create the downstream work. It just was not carrying the information people needed to do that work.

The Manual Workaround

Every handoff recreated work that had already been done.

When someone received one of these downstream tickets, they first had to figure out which PPL request it came from.

Then they had to open the PPL project, locate the original request, review everything that had been entered, and manually copy that information into the ticket they would actually work from.

That could include descriptions, dates, custom information, links, and attachments.

And because the transfer was manual, there was always the possibility that something would be missed.

An attachment could be overlooked. A field could be skipped. Someone could forget where the source ticket was and have to search for it again later.

This happened whenever new downstream work was created from a PPL.

If someone already entered the information once, why are we asking someone else to enter it again?

Why It Mattered

A small handoff problem becomes expensive when it repeats for months.

A single copy-and-paste action might not look like a major operational problem.

But PPLs were not one-off tasks.

They could run for much of the year and involve several departments, each receiving their own downstream work throughout the project.

That meant the same broken handoff could repeat again and again across the life of one PPL, then repeat again across every other active PPL.

The burden also fell on the people doing the downstream work, not the person who had already entered the information.

The workflow was creating a hidden administrative tax at every team handoff.

Hidden Cost

  • Repeated duplicate data entry
  • Time spent locating source requests
  • Risk of missing attachments or context
  • Two tickets to reference instead of one working ticket
  • Repeated across long‑running projects and multiple teams

The First Attempt

Asana AI was being tested, but it was not solving the problem reliably.

At the time, Asana had introduced AI capabilities and the team had access to trial credits for experimentation.

My manager and the person responsible for Asana administration were exploring whether AI could solve several workflow problems, including the PPL handoff.

But the experimentation was consuming the available credits very quickly, and the copying behavior still was not working the way they needed it to.

I started researching whether the information transfer actually required AI at all.

It did not.

The underlying problem could be handled directly through Asana's API.

The Shift

  • Move away from a credit-dependent AI approach
  • Use deterministic API logic instead
  • Trigger the workflow from the actual task creation event
  • Copy the required information directly

What I Built

An integration that completed the handoff automatically.

I researched the Asana API and built a Node.js integration that watched for the downstream tickets created from PPL requests.

When one of those tickets was created, the integration automatically identified the related source request and populated the downstream ticket with the information needed to begin work.

The goal was simple:

When the system creates work for another team, the context required to perform that work should travel with it.

I used Insomnia while working with and testing the API, then tested the integration directly against Asana from my local development environment.

Testing & Status

The integration was working locally. Deployment was the remaining step.

I tested the integration by creating the relevant work in Asana and verifying that the downstream tickets were populated automatically.

The original copying requirements were functioning, and I added additional context that made the resulting ticket easier for the employee to use, including the direct link back to the source request and the auto-copy note.

At that point, the functional development work was complete in my local environment.

The remaining step was hosting the integration so it could run independently for everyone rather than from my machine.

Cloudflare was the planned deployment environment.

What Was Planned Next

Once the integration layer worked, the next question was what else the system could enforce.

The PPL copying workflow was the first major problem I tackled.

Once that was working locally, the plan was to use the same technical approach for additional operational rules inside Asana.

One of the next planned automations involved story points.

Team members had a weekly capacity target of approximately 15 points, while different types of work carried different point values.

A single email might represent three points. A larger email series could represent five or six. More complex recurring programs could consume even more capacity.

The planned automation would help keep newly assigned work from pushing someone beyond the weekly capacity model and move appropriate work into the following week when necessary.

That phase was planned, but I did not build it before leaving the organization.

Planned Extension

  • Read assigned task story points
  • Compare weekly workload against capacity
  • Prevent silent over-allocation
  • Move appropriate work into the next week
  • Turn an operating rule into system behavior

The Bigger Lesson

An automated task is not the same as an automated handoff.

The original PPL workflow had already automated an important step.

It could create work for the correct downstream team without asking someone to build every ticket manually.

But automation should be evaluated by what the next person can actually do when it finishes.

If the system creates a ticket and the employee still has to search for the original request, copy the description, transfer the attachments, find the due date, and reconstruct the context, then part of the handoff is still manual.

The better question is not simply, “Did the system create the next task?”

It is:

“Did the system give the next person what they need to act?”

Systems Lesson

  • Automating task creation is only part of a handoff
  • Context should travel with the work
  • Repeated copying is a signal to inspect the system boundary
  • Deterministic integrations can solve problems that do not require AI
  • Good automation removes administrative work before execution begins
Automation is not complete just because the system created the next task. The handoff is complete when the next person has what they need to act.
